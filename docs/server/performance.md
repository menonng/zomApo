# 서버 성능: RAM·CPU·플랫폼(Fabric 유지 vs Folia)

2026-11-20 실측 + 시뮬레이션. 인원 가정: **전체 최대 20±3명, 활성(하루 2시간 이상) 8~10+α명, 동시 접속 15명 이상도 가능.** 월드 8,000 × 8,000.

서버 PC: **Ryzen 5 9600X · DDR5 32GB · Windows 11, 같은 PC 에서 마크 클라이언트(힙 8~12GB)도 실행** → 바로 [9절](#9-이-서버-pc-ryzen-5-9600x--ddr5-32gb--windows-11).

## 0. 결론

| 질문 | 결정 | 근거 |
|---|---|---|
| 플랫폼 | **Fabric 모드 유지 + 최적화 모드.** Folia(플러그인 전환) 안 함 | 이 인원에서는 Fabric + 최적화 모드로 틱 예산(50ms) 안에 들어온다. Folia 는 16코어 권장, 스코어보드 API 전체가 미지원이라 '국가 = 바닐라 팀' 설계와 정면으로 부딪히고, 모드 4개를 다 다시 짜야 한다(6절) |
| 서버 힙 | **`-Xms8G -Xmx8G`** (동시 접속 12명 이하만 보면 6GB) | 실사용 힙(GC 직후)은 동시 15~23명이 넓게 흩어진 순간 봇 실측 1.6~2.2GB, 실제 플레이·월드 성장분을 얹으면 2.6~3.3GB. G1 이 여유 있게 돌려면 그 2.5배 안팎 |
| BlueMap | 서버 힙 안에서 같이 돌아간다. **첫 전체 렌더는 개장 전에** 끝내 두고, 운영 중 렌더 스레드는 1~2개 | 렌더 스레드 1개가 실사용 힙 +0.2~0.4GB, CPU 코어 1개를 쓴다. 틱은 중앙값 거의 그대로, 95백분위 최대 +30% (2-3) |
| 더 줘야 할 때 | 운영 중 BlueMap 렌더 스레드를 3개 이상 쓰거나 BlueMap·squaremap 을 동시에 렌더하면 **+1~2GB** | 4절 |
| 더 줘도 소용없는 것 | 10GB 이상 | 틱 시간(렉)은 RAM 이 아니라 **CPU 단일 코어 성능**이 정한다. 힙만 키우면 GC 한 번이 길어질 뿐이다 |
| 최적화 모드 | Lithium, FerriteCore, Krypton, C2ME, ScalableLux, VMP, Clumps (모두 26.3 빌드 있음, 서버 전용) | 같은 조건에서 틱 시간 −20~25%, 실사용 힙 −20%, 할당량 −25% (2절) |
| 거리 설정 | `view-distance=10`, `simulation-distance=6` (부족하면 시야 8) | 시야 8·시뮬 6 은 틱 −14%, 힙 −15% (2절) |
| 월드 | 월드 경계(반경 4,000, 25만 청크) 안 **전부 Chunky 로 사전 생성** | 측정은 미리 생성한 월드 기준이다. 탐험 중 생성은 순간 렉의 가장 큰 원인. 비용은 10절 |
| 안전장치 | 부하 연동 몹 상한(zomApo), ServerCore(시야·시뮬레이션 거리 자동 축소) | 동시 15명 이상이 넓게 흩어지면 틱 예산을 넘는 순간이 생긴다(3-2) |

**가장 중요한 발견: 렉은 '몇 명이 접속했나'보다 '몇 군데로 흩어져 있나'로 정해진다.** 떨어진 무리 하나가 틱 시간 약 4.7ms(최적화 모드, 측정 컨테이너 기준)를 더하고, 같은 무리에 한 명 더 붙는 비용은 거의 0이다. 그래서 국가 기지에 모여 있는 시간이 많을수록 가볍다.

## 3. 인원 시뮬레이션: 실제로 몇 명이 몇 군데에 있나

`tools/sim/load_sim.py` (300회 × 23일 × 매시). 접속 모델은 [simulation.md](simulation.md) 의 유형별 접속 확률·세션 길이를 그대로 쓰고, 접속자를 무리로 나눈다: 접속 중 55% 는 자국 기지, 밖에 나간 사람은 35% 확률로 같은 국가 접속자와 같이 다닌다.

| 전체/활성 | 저녁(19~24시) 평균 동시접속 | 상위 5% | 상위 1% | 시즌 최대 | 떨어진 무리 상위 5% | 최대 |
|---|---|---|---|---|---|---|
| 17/8 | 2.7 | 5 | 6 | 10 | 4 | 8 |
| 20/10 | 3.3 | 6 | 7 | 12 | 5 | 10 |
| 23/12 | 3.9 | 7 | 8 | 13 | 5 | 10 |
| (이전 가정) 15/4 | 1.7 | 3 | 5 | 8 | 3 | 7 |

'최대 20명'이라도 **한 번에 들어와 있는 사람은 대개 3~4명, 붐빌 때 7~8명, 시즌 최고 12~13명**이다(개장 첫날 같은 순간).

### 3-1. CPU 등급별 예상 (20/10, 최적화 모드, 실제 플레이 보정 ×1.5)

봇은 가만히 서 있으므로, 실제 플레이(이동·청크 로드·전투·건축)는 1.5배로 보정했다(가정). CPU 배율은 측정 컨테이너 대비 대략값이다(가정).

| CPU 단일 코어 | 틱 95백분위의 상위 1% | 시즌 최악 순간 | 느려지는 시간(틱 95% > 50ms) |
|---|---|---|---|
| 구형 노트북·저전력 (8세대 i5 U 급) | 58ms | 95ms | 2.2% |
| 측정 컨테이너 (클라우드 Xeon 2.1GHz) | 52ms | 86ms | 2.2% |
| 보급형 데스크톱 (Ryzen 5 3600, i5-10400 급) | 37ms | 61ms | 0.01% |
| 최근 데스크톱 (Ryzen 5 5600·7600, i5-12400~13400 급) | 29ms | 48ms | 0% |
| 고성능 (Ryzen 7 7800X3D, i7-13700 이상) | 23ms | 37ms | 0% |

최적화 모드 없이(기본) 같은 표를 돌리면 구형 노트북급 20%, 측정 컨테이너급 7.8%, 보급형 데스크톱 0.5% 의 시간 동안 느려진다.

민감도: 플레이어가 기지에 덜 모이면(기지 30%, 동행 15%) 최적화 모드 기준 구형 노트북급 5.0%, 보급형 데스크톱 0.1%, 최근 데스크톱 0%.

### 3-2. 동시 접속을 정해 놓고 (스트레스, 9600X 기준)

시즌 시뮬레이션의 최대는 12~13명이지만, 개장일·블러드문·주말 저녁에 15명 이상이 몰릴 수 있다. 접속자를 세 국가에 고르게 나누고 무리 모델을 그대로 적용해 5,000번 뽑았다(최적화 모드, CPU 배율 1.8 = 9600X 에서 클라이언트도 함께 실행, 실제 플레이 ×1.5). 원자료: [tools/sim/load-results-9600x.md](../../tools/sim/load-results-9600x.md).

틱 **중앙값**이 50ms 를 넘으면 TPS 자체가 떨어지고, **95백분위**만 넘으면 가끔 끊기는 정도다.

| 동시 접속 | 보통 무리 모델: TPS 20 유지 / 가끔 끊김 | 넓은 월드로 더 흩어짐: TPS 20 유지 / 가끔 끊김 | 넓은 월드 + 시야 8·시뮬 6: 붐빌 때 틱 95% |
|---|---|---|---|
| 10명 | 100% / 0% | 100% / 0% | 40ms |
| 12명 | 100% / 1% | 100% / 12% | 44ms |
| 15명 | 100% / 7% | 89% / 49% | 52ms |
| 18명 | 97% / 21% | 60% / 78% | 59ms |
| 20명 | 92% / 34% | 40% / 89% | 63ms |

- 보통 무리 모델 = 접속 중 55% 는 자국 기지, 밖에 나간 사람은 35% 확률로 동행. 넓은 월드 = 기지 40%, 동행 20%.
- **15명까지는 문제없고, 18명 이상이 넓게 흩어지면 TPS 가 떨어지기 시작한다.** 그래서 두 가지 안전장치를 둔다.
  1. **부하 연동 몹 상한**(zomApo): 틱 중앙값 35ms 부터 몬스터 상한을 ×0.8, 45ms 부터 ×0.6. 좀비 ×2 의 비용이 틱의 약 17% 라(2-3), 이것만으로 10% 안팎을 덜어 낸다([zombification.md](../design/zombification.md) 2-1).
  2. **ServerCore**: 틱이 높을 때 시뮬레이션 거리를 자동으로 6 → 4 까지 줄인다(측정에서 시야 8·시뮬 6 이 −16%).
  둘을 합치면 20명이 넓게 흩어진 최악에서도 틱 중앙값이 40ms 안팎으로 내려온다(추정).
- 블러드문·거점전 같은 행사는 사람을 한곳에 모으므로 오히려 가볍다(떨어진 무리 수가 준다).

## 4. RAM

| 항목 | 값 | 근거 |
|---|---|---|
| 실사용 힙 (봇, 시즌 최대 순간) | 약 1.3GB (최적화) / 1.5GB (기본) | 3절 분포 × 2-4 모델 |
| + 실제 플레이·월드 성장 | ×1.3 + 0.5GB → **약 2.2GB** | 이동 중 캐시된 청크, 건축물의 블록 엔티티(상자·화로·호퍼), 농장, 망자 좀비, 주민 (가정) |
| 할당 속도 | 100~230 MB/s (최적화) | GC 로그 |
| 동시 15~23명이 넓게 흩어진 순간 | 봇 1.6~2.2GB → 보정 후 **2.6~3.3GB** | 3-2 |
| **권장 힙** | **8GB** (동시 12명 이하만 보면 6GB) | 실사용의 2.5배 안팎. 젊은 세대에 2GB 이상을 줄 수 있어 young GC 가 몇 초에 한 번으로 줄고, 혼합 GC 여유가 남는다 |
| 최소 | 4GB | 돌아가지만 GC 가 잦다 |
| BlueMap 렌더 | +0.2~0.4GB (스레드 1개) | 2-3. 스레드를 늘리면 비례해서 는다 |
| JVM 힙 밖 메모리 | 약 0.7~0.9GB | 측정 RSS − 힙 (메타스페이스, 코드 캐시, 스레드, 네트워크 버퍼) |

기계 전체에 필요한 메모리:

| 항목 | 서버 전용 기계 | 같은 PC 에서 직접 플레이도 함 |
|---|---|---|
| 마크 서버 (힙 6GB + 힙 밖 0.9GB) | 6.9GB | 6.9GB |
| 디스코드 봇 (JVM) | 0.4GB | 0.4GB |
| 운영체제·기타 | 2GB | 2GB |
| 마크 클라이언트 (Sodium 기준) | | 4~6GB |
| 디스코드·브라우저 | | 1~2GB |
| **합계** | **약 9~10GB → RAM 16GB 면 충분** | **약 15~17GB → 16GB 는 빠듯, 32GB 권장.** 16GB 에서 같이 쓰면 서버 힙을 4~5GB 로 |

GC: 측정 컨테이너(4코어)에서 young GC 정지 평균 30~80ms. 코어가 많은 PC 에서는 더 짧다. 정지가 체감되면 Java 25 의 세대별 ZGC(`-XX:+UseZGC`)를 spark 로 비교해 본다(정지 1ms 안팎, 대신 CPU 를 조금 더 씀).

python ../sim/load_sim.py --cost work/results/cost.json   # 그 PC 기준 동시 접속별 힙·틱 분포

요약의 opt-nations-x2 에서 봇 12명 MSPT 95% 가 35ms 안쪽이면 이 인원에 넉넉하다(실제 플레이 ×1.5 를 해도 50ms 안). 이 경우 load_sim 의 3절 표는 'CPU 배율 1.0' 행이 그 PC 다.

## 6. Folia(또는 Paper) 로 전환하면?

| 항목 | Fabric + 최적화 모드 (현재) | Paper 플러그인 | Folia 플러그인 |
|---|---|---|---|
| 이 인원에서의 틱 여유 | 최근 데스크톱이면 시즌 내내 50ms 안 | Fabric + 최적화와 비슷(Paper 의 최적화 ≈ Lithium·VMP·C2ME·ScalableLux) | 무리마다 스레드가 갈려 최악 지역 틱 11~14ms(가정 계산). 하지만 Fabric 이 이미 50ms 안이면 체감 차이 0 |
| 이득이 나는 조건 | | | 플레이어가 많고 넓게 퍼진 서버, **최소 16코어**(공식 권장) |
| 국가 = 바닐라 팀 | 그대로 | 그대로 | **스코어보드 API 전체가 '고장' 목록**. 팀 색·아군 피해 끔·국가 채팅·알파 좀비 발광색 모두 다시 설계 |
| 믹스인 | 자유 (좀비 변환, 팀 메시지 경로 등) | 없음. 이벤트 + NMS 직접 접근으로 대체 | 없음 + 모든 코드가 지역 스레드 규칙(`RegionScheduler`/`EntityScheduler`)을 지켜야 함 |
| 전역 시스템 (감염 램프, 블러드문, 국가 영토, 생존일지 이벤트) | 단일 스레드라 단순 | 단일 스레드 | 여러 지역이 동시에 읽고 쓰므로 스레드 안전하게 다시 짜야 함 |
| couriersRoost | Fabric 모드 그대로 | Paper 포팅 필요 | Folia 포팅 필요(전서구가 지역 사이를 날아감) |
| 텔레포트 | 그대로 | 그대로 | `Entity#teleport` 영구 제거, `teleportAsync` 만 |
| 기존 플러그인 생태계 | | 넓음 | "호환성 기대치는 0"(공식). `folia-supported` 표시가 있는 것만 로드 |

| 다시 짜야 하는 것 | 없음 | zomApo, simpleNationWar, snw-discord, couriersRoost | 같은 4개 + 스레드 모델 |
| 26.x 지원 | 26.3 | 26.3 안정 빌드 있음 | 26.3 안정 빌드 있음. 새 버전은 보통 Paper 보다 늦음 |

**결론: 전환하지 않는다.** Folia 가 실제로 이득을 주는 순간은 "Fabric 이 50ms 를 넘는 시간"뿐인데, 최적화 모드를 넣으면 보급형 데스크톱 이상에서 그 시간이 0.01% 이하다. 그 대가가 모드 전부 재작성 + 국가 시스템 재설계 + 16코어다. CPU 가 약한 기계라면 Folia 보다 **기계를 바꾸거나 시야·시뮬레이션 거리를 줄이는 쪽**이 훨씬 싸다.

다시 볼 조건: 동시 접속이 상시 25명을 넘고 넓게 흩어지는 시즌, 또는 서버 기계가 16코어 이상이고 단일 코어가 약할 때.

### 6-1. Fabric 모드 서버 vs Paper 플러그인 서버

| 질문 | 답 |
|---|---|
| 기본 성능 | **아무것도 안 넣은 Fabric 은 Paper 보다 느리다.** Paper 는 청크 시스템·엔티티 처리·조명 등에 최적화가 기본으로 들어 있다 |
| 최적화 모드를 넣으면 | Lithium·C2ME·ScalableLux(또는 Moonrise = Paper 의 청크 시스템 이식)·VMP·FerriteCore·Krypton 을 넣은 Fabric 은 Paper 와 비슷한 수준이다. 이 서버 실측에서 최적화 모드가 틱 −20~25%, 힙 −20% (2-1). Paper 를 직접 재지는 않았다(Carpet 봇이 Fabric 전용) |
| Paper 만의 '빠름' | 일부는 바닐라 동작을 바꿔서 얻는다: 엔티티 활성 범위(멀리 있는 몹을 덜 움직임), 일부 농장·복제 동작 차이. Fabric 최적화 모드는 바닐라 동작을 지키는 쪽이다 |
| 리소스팩 | **차이 없다.** 커스텀 외형은 어느 쪽이든 리소스팩이 필요하다 |
| 모드의 이점 | 믹스인으로 게임 내부를 직접 바꾼다: 원종 AI 를 살린 좀비화, 상태 효과 등록, 채팅 경로, 망자 피해 규칙. 플러그인은 Paper API 가 열어 둔 곳까지만 쉽고, 나머지는 NMS(내부 코드) 직접 접근이라 버전마다 깨진다 |
| 이미 있는 것 | couriersRoost 가 Fabric 모드다. Kotlin 모드 3개도 Fabric 기준으로 짜여 있다 |
| 관리 콘솔 | Paper 콘솔(색, 자동완성)이 기본으로 더 낫다. Fabric 은 **Better Fabric Console**(26.3 지원)로 같은 수준이 된다. 서버 창(플레이어 목록·로그·명령 입력)은 바닐라 서버 GUI 라 둘 다 같다 |

결론: Paper 로 갈 이유는 '최적화 모드를 고르는 수고'를 줄이는 것 정도다. 그 대가가 모드 전부 재작성이라 Fabric 을 유지한다.

## 8. 한계와 가정

- 봇은 움직이지 않는다. 탐험·건축·레드스톤·농장 비용은 '실제 플레이 ×1.5' 와 '힙 ×1.3 + 0.5GB' 가정으로만 들어가 있다. 개장 리허설 때 spark 로 실제 값을 다시 잰다.
- CPU 등급 배율은 공개 벤치마크 경향에서 잡은 대략값이다. 5절로 직접 재는 것이 정확하다.
- zomApo 의 좀비 변환·변종 로직은 아직 구현 전이다. 좀비 ×2 는 바닐라 좀비를 더 소환해 흉내 냈고, 변종 AI(러너·디거 등)의 추가 비용은 들어 있지 않다.
- 측정 기계는 다른 작업과 CPU 를 나눠 쓰는 클라우드라 같은 조건도 ±10% 흔들린다.

|---|---|---|
| Windows 11 + 백그라운드 | 4GB | 4GB |
| 디스코드·브라우저 | 2GB | 2GB |

### 9-3. 실행 설정 (Windows)

`start.bat` 예:

```bat
@echo off
start "zomApo" /abovenormal /wait java -Xms8G -Xmx8G -XX:+UseG1GC -XX:+ParallelRefProcEnabled -XX:MaxGCPauseMillis=200 ^
 -XX:+UnlockExperimentalVMOptions -XX:G1NewSizePercent=30 -XX:G1MaxNewSizePercent=40 -XX:G1HeapRegionSize=8M ^
 -XX:G1ReservePercent=20 -XX:InitiatingHeapOccupancyPercent=15 -XX:ParallelGCThreads=4 -XX:ConcGCThreads=2 ^
 -jar fabric-server-launch.jar nogui
```

| 설정 | 이유 |
|---|---|
| `/abovenormal` | 게임 모드가 앞에 띄운 클라이언트를 우선하므로, 뒤에 있는 서버가 밀리지 않게 한 단계 올린다 |
| `ParallelGCThreads=4`, `ConcGCThreads=2` | GC 가 12스레드를 다 잡으면 클라이언트 프레임이 튄다. 서버 GC 는 4스레드로 충분하다 |
| `AlwaysPreTouch` 뺌 | 서버 전용 기계가 아니라서, 쓰지 않는 힙까지 처음부터 물리 메모리로 잡지 않게 |
| C2ME 스레드 3 (`config/c2me.toml` 의 `globalExecutorParallelism`) | 사전 생성 때만 기본값(코어 수), 운영 중에는 3 |
| BlueMap 렌더 스레드: 운영 중 1, 개장 전 전체 렌더 때 10 | 10절 |
| Windows 보안 실시간 검사에서 서버 폴더 제외 | 리전 파일·BlueMap 타일 쓰기가 많다. 제외하면 저장·렌더가 눈에 띄게 빨라진다 |
| 전원 관리 '균형 조정' 그대로 | Ryzen 9000 은 균형 모드에서 부스트가 정상 동작한다 |
| 서버 폴더는 NVMe SSD | 월드 약 3GB + BlueMap 약 10GB + 백업 |

자기 PC 기준 숫자를 확정하려면 5절대로 `python bench.py all` 을 돌리고(클라이언트를 켠 상태와 끈 상태 각각), 나온 cost.json 으로 load_sim 을 다시 돌린다.

## 10. 월드 8,000 × 8,000 의 비용

| 항목 | 값 | 근거 |

| 흩어짐 | 넓을수록 떨어진 무리가 늘어 15명 이상 동시 접속 때 부하가 오른다 | 3-2 '넓은 월드' 열 |

개장 전 순서: 26.4 월드 생성 → Chunky 로 25만 청크 사전 생성 → BlueMap 전체 렌더(스레드 10) → 렌더 스레드 1 로 낮추고 개장. 첫 렌더 이후에는 바뀐 청크만 다시 그린다.
