# 서버 성능: RAM·CPU·플랫폼(Fabric 유지 vs Folia)

2026-11-20 실측 + 시뮬레이션. 인원 가정: **전체 최대 20±3명, 활성(하루 2시간 이상) 8~10+α명.**

## 0. 결론

| 질문 | 결정 | 근거 |
|---|---|---|
| 플랫폼 | **Fabric 모드 유지 + 최적화 모드.** Folia(플러그인 전환) 안 함 | 이 인원에서는 Fabric + 최적화 모드로 틱 예산(50ms) 안에 들어온다. Folia 는 16코어 권장, 스코어보드 API 전체가 미지원이라 '국가 = 바닐라 팀' 설계와 정면으로 부딪히고, 모드 4개를 다 다시 짜야 한다(6절) |
| 서버 힙 | **`-Xms6G -Xmx6G`** | 실사용 힙(GC 직후)은 시즌 최대 순간에도 1.3GB 안팎(봇 실측), 실제 플레이·월드 성장분을 얹어도 2~2.5GB. G1 이 여유 있게 돌려면 그 2.5~3배 |
| 더 줘야 할 때 | BlueMap 첫 전체 렌더를 사람이 있을 때 돌리거나 BlueMap·squaremap 을 같이 돌리면 **8GB** | 4절 |
| 더 줘도 소용없는 것 | 10GB 이상 | 틱 시간(렉)은 RAM 이 아니라 **CPU 단일 코어 성능**이 정한다. 힙만 키우면 GC 한 번이 길어질 뿐이다 |
| 최적화 모드 | Lithium, FerriteCore, Krypton, C2ME, ScalableLux, VMP, Clumps (모두 26.3 빌드 있음, 서버 전용) | 같은 조건에서 틱 시간 −20~25%, 실사용 힙 −20%, 할당량 −25% (2절) |
| 거리 설정 | `view-distance=10`, `simulation-distance=6` (부족하면 시야 8) | 시야 8·시뮬 6 은 틱 −14%, 힙 −15% (2절) |
| 월드 | 월드 경계(반경 2,000) 안 **전부 Chunky 로 사전 생성** | 측정은 미리 생성한 월드 기준이다. 탐험 중 생성은 순간 렉의 가장 큰 원인 |

**가장 중요한 발견: 렉은 '몇 명이 접속했나'보다 '몇 군데로 흩어져 있나'로 정해진다.** 떨어진 무리 하나가 틱 시간 약 4.7ms(최적화 모드, 측정 컨테이너 기준)를 더하고, 같은 무리에 한 명 더 붙는 비용은 거의 0이다. 그래서 국가 기지에 모여 있는 시간이 많을수록 가볍다.

## 3. 인원 시뮬레이션: 실제로 몇 명이 몇 군데에 있나

`tools/sim/load_sim.py` (300회 × 23일 × 매시). 접속 모델은 [simulation.md](simulation.md) 의 유형별 접속 확률·세션 길이를 그대로 쓰고, 접속자를 무리로 나눈다: 접속 중 55% 는 자국 기지, 밖에 나간 사람은 35% 확률로 같은 국가 접속자와 같이 다닌다.

| 전체/활성 | 저녁(19~24시) 평균 동시접속 | 상위 5% | 상위 1% | 시즌 최대 | 떨어진 무리 상위 5% | 최대 |
|---|---|---|---|---|---|---|
| 17/8 | 2.7 | 5 | 6 | 10 | 4 | 8 |
| 20/10 | 3.3 | 6 | 7 | 12 | 5 | 10 |
| 23/12 | 3.9 | 7 | 8 | 13 | 5 | 10 |
| (이전 가정) 15/4 | 1.7 | 3 | 5 | 8 | 3 | 7 |

'최대 20명'이라도 **한 번에 들어와 있는 사람은 대개 3~4명, 붐빌 때 7~8명, 시즌 최고 12~13명**이다(개장 첫날 같은 순간).

### 3-1. CPU 등급별 예상 (20/10, 최적화 모드, 실제 플레이 보정 ×1.5)

봇은 가만히 서 있으므로, 실제 플레이(이동·청크 로드·전투·건축)는 1.5배로 보정했다(가정). CPU 배율은 측정 컨테이너 대비 대략값이다(가정).

| CPU 단일 코어 | 틱 95백분위의 상위 1% | 시즌 최악 순간 | 느려지는 시간(틱 95% > 50ms) |
|---|---|---|---|
| 구형 노트북·저전력 (8세대 i5 U 급) | 58ms | 95ms | 2.2% |
| 측정 컨테이너 (클라우드 Xeon 2.1GHz) | 52ms | 86ms | 2.2% |
| 보급형 데스크톱 (Ryzen 5 3600, i5-10400 급) | 37ms | 61ms | 0.01% |
| 최근 데스크톱 (Ryzen 5 5600·7600, i5-12400~13400 급) | 29ms | 48ms | 0% |
| 고성능 (Ryzen 7 7800X3D, i7-13700 이상) | 23ms | 37ms | 0% |

최적화 모드 없이(기본) 같은 표를 돌리면 구형 노트북급 20%, 측정 컨테이너급 7.8%, 보급형 데스크톱 0.5% 의 시간 동안 느려진다.

민감도: 플레이어가 기지에 덜 모이면(기지 30%, 동행 15%) 최적화 모드 기준 구형 노트북급 5.0%, 보급형 데스크톱 0.1%, 최근 데스크톱 0%.

## 4. RAM

| 항목 | 값 | 근거 |
|---|---|---|
| 실사용 힙 (봇, 시즌 최대 순간) | 약 1.3GB (최적화) / 1.5GB (기본) | 3절 분포 × 2-4 모델 |
| + 실제 플레이·월드 성장 | ×1.3 + 0.5GB → **약 2.2GB** | 이동 중 캐시된 청크, 건축물의 블록 엔티티(상자·화로·호퍼), 농장, 망자 좀비, 주민 (가정) |
| 할당 속도 | 100~230 MB/s (최적화) | GC 로그 |
| **권장 힙** | **6GB** | 실사용의 2.5~3배. 젊은 세대에 2GB 이상을 줄 수 있어 young GC 가 몇 초에 한 번으로 줄고, 혼합 GC 여유가 남는다 |
| 최소 | 4GB | 돌아가지만 GC 가 잦다 |
| BlueMap 렌더 | 측정 중 | 2-3 |
| JVM 힙 밖 메모리 | 약 0.7~0.9GB | 측정 RSS − 힙 (메타스페이스, 코드 캐시, 스레드, 네트워크 버퍼) |

기계 전체에 필요한 메모리:

| 항목 | 서버 전용 기계 | 같은 PC 에서 직접 플레이도 함 |
|---|---|---|
| 마크 서버 (힙 6GB + 힙 밖 0.9GB) | 6.9GB | 6.9GB |
| 디스코드 봇 (JVM) | 0.4GB | 0.4GB |
| 운영체제·기타 | 2GB | 2GB |
| 마크 클라이언트 (Sodium 기준) | | 4~6GB |
| 디스코드·브라우저 | | 1~2GB |
| **합계** | **약 9~10GB → RAM 16GB 면 충분** | **약 15~17GB → 16GB 는 빠듯, 32GB 권장.** 16GB 에서 같이 쓰면 서버 힙을 4~5GB 로 |

GC: 측정 컨테이너(4코어)에서 young GC 정지 평균 30~80ms. 코어가 많은 PC 에서는 더 짧다. 정지가 체감되면 Java 25 의 세대별 ZGC(`-XX:+UseZGC`)를 spark 로 비교해 본다(정지 1ms 안팎, 대신 CPU 를 조금 더 씀).

## 5. 자기 PC 에서 재기

정확한 숫자는 실제 서버를 돌릴 기계에서 재는 게 가장 좋다. 같은 측정을 그대로 돌린다.

```
cd zomApo && ./gradlew buildAll        (simpleNationWar 도 옆 폴더에서 buildAll)
cd tools/perf
python bench.py all                    # 월드 생성 약 15분 + 표준 4조합 약 45분, 끝나면 요약과 비용 모델 출력
python ../sim/load_sim.py --cost work/results/cost.json   # 출력된 비용 모델을 cost.json 으로 저장한 뒤
```

요약의 '최적화 모드, 국가 배치' 행에서 봇 12명 MSPT 95% 가 35ms 안쪽이면 이 인원에 넉넉하다.

## 6. Folia(또는 Paper) 로 전환하면?

| 항목 | Fabric + 최적화 모드 (현재) | Paper 플러그인 | Folia 플러그인 |
|---|---|---|---|
| 이 인원에서의 틱 여유 | 최근 데스크톱이면 시즌 내내 50ms 안 | Fabric + 최적화와 비슷(Paper 의 최적화 ≈ Lithium·VMP·C2ME·ScalableLux) | 무리마다 스레드가 갈려 최악 지역 틱 11~14ms(가정 계산). 하지만 Fabric 이 이미 50ms 안이면 체감 차이 0 |
| 이득이 나는 조건 | | | 플레이어가 많고 넓게 퍼진 서버, **최소 16코어**(공식 권장) |
| 국가 = 바닐라 팀 | 그대로 | 그대로 | **스코어보드 API 전체가 '고장' 목록**. 팀 색·아군 피해 끔·국가 채팅·알파 좀비 발광색 모두 다시 설계 |
| 믹스인 | 자유 (좀비 변환, 팀 메시지 경로 등) | 없음. 이벤트 + NMS 직접 접근으로 대체 | 없음 + 모든 코드가 지역 스레드 규칙(`RegionScheduler`/`EntityScheduler`)을 지켜야 함 |
| 전역 시스템 (감염 램프, 블러드문, 국가 영토, 생존일지 이벤트) | 단일 스레드라 단순 | 단일 스레드 | 여러 지역이 동시에 읽고 쓰므로 스레드 안전하게 다시 짜야 함 |
| couriersRoost | Fabric 모드 그대로 | Paper 포팅 필요 | Folia 포팅 필요(전서구가 지역 사이를 날아감) |
| 텔레포트 | 그대로 | 그대로 | `Entity#teleport` 영구 제거, `teleportAsync` 만 |
| 기존 플러그인 생태계 | | 넓음 | "호환성 기대치는 0"(공식). `folia-supported` 표시가 있는 것만 로드 |
| 지도 | BlueMap·squaremap Fabric | 둘 다 | 둘 다 Folia 빌드 있음 |
| 다시 짜야 하는 것 | 없음 | zomApo, simpleNationWar, snw-discord, couriersRoost | 같은 4개 + 스레드 모델 |
| 26.x 지원 | 26.3 | 26.3 안정 빌드 있음 | 26.3 안정 빌드 있음. 새 버전은 보통 Paper 보다 늦음 |

**결론: 전환하지 않는다.** Folia 가 실제로 이득을 주는 순간은 "Fabric 이 50ms 를 넘는 시간"뿐인데, 최적화 모드를 넣으면 보급형 데스크톱 이상에서 그 시간이 0.01% 이하다. 그 대가가 모드 전부 재작성 + 국가 시스템 재설계 + 16코어다. CPU 가 약한 기계라면 Folia 보다 **기계를 바꾸거나 시야·시뮬레이션 거리를 줄이는 쪽**이 훨씬 싸다.

다시 볼 조건: 동시 접속이 상시 25명을 넘고 넓게 흩어지는 시즌, 또는 서버 기계가 16코어 이상이고 단일 코어가 약할 때.

## 8. 한계와 가정

- 봇은 움직이지 않는다. 탐험·건축·레드스톤·농장 비용은 '실제 플레이 ×1.5' 와 '힙 ×1.3 + 0.5GB' 가정으로만 들어가 있다. 개장 리허설 때 spark 로 실제 값을 다시 잰다.
- CPU 등급 배율은 공개 벤치마크 경향에서 잡은 대략값이다. 5절로 직접 재는 것이 정확하다.
- zomApo 의 좀비 변환·변종 로직은 아직 구현 전이다. 좀비 ×2 는 바닐라 좀비를 더 소환해 흉내 냈고, 변종 AI(러너·디거 등)의 추가 비용은 들어 있지 않다.
- 측정 기계는 다른 작업과 CPU 를 나눠 쓰는 클라우드라 같은 조건도 ±10% 흔들린다.
